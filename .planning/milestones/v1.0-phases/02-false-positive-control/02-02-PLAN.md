<objective>
Deliver the inline-ignore vertical slice (SUP-01): a developer can paste
`// mimir:ignore` (or `mimir:ignore:<rule-id>`) on the secret's line and that
finding disappears from `mimir scan` — end to end, scanner → output → exit code.
Under `--verbose`, every reported finding shows the exact paste-ready directive
plus its fingerprint (criterion 1), so the user knows precisely what to add.

This plan also OWNS the `--show-suppressed` flag definition and the
scanner-loop annotate-vs-drop branch for inline-ignore (D-12). When
`--show-suppressed` is OFF, inline-ignored findings DROP at scan time (the
common case). When it is ON, inline-ignored findings are KEPT and annotated
(`Suppressed=true; SuppressionReason="inline-ignore"`) so they survive to the
post-`g.Wait()` output stage that Plan 04's shared `--show-suppressed` renderer
re-includes — without this, an inline-ignored finding could never be surfaced
by `--show-suppressed`, violating D-12's three-reason audit guarantee.

Purpose: This is the first and lowest-risk suppression layer and the most common
day-to-day false-positive escape hatch. It exercises the full pipeline (per-line
detection → drop/annotate → output → unchanged exit code), proving the slice works
before the heavier path-prune and baseline layers land.
Output: internal/suppress/inline.go (+ test), inline annotate-vs-drop wiring in
scanFile, the `--show-suppressed` flag definition + scanner plumbing, the
--verbose hint in human output, the --verbose hint flag/wiring + CLI tests
(including the inline-ignore `--show-suppressed` re-inclusion test).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| repo file line text → directive parser | Untrusted line content drives InlineSuppresses; a malformed/partial directive must fail safe (not suppress unrelated rules) |
| concurrent walk → shared Stats counters | Inline-ignored count is incremented from per-file goroutines |
| --show-suppressed flag → scanner annotate-vs-drop branch | The flag must deterministically choose KEEP+annotate vs DROP; a wrong default could leak suppressed findings into normal output or hide them from the audit |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-03 | Tampering (trust erosion) | over-broad inline suppression | mitigate | Parse the optional `:rule-id` scope (Pattern 1); scoped form suppresses ONLY the named rule (Pitfall 3 test); inline-ignored findings are counted in the D-11 summary so suppression is never silent |
| T-02-04 | Repudiation | inline-ignored finding flips CI green when it should not | accept | Inline ignore is an explicit, same-line, developer-authored opt-out (D-01); the count is always shown (D-11) and --verbose shows the exact directive. Exit code excludes only the explicitly-ignored finding; --show-suppressed (D-12) re-surfaces it for audit |
| T-02-05 | Denial of Service | data race on the inline-ignored counter | mitigate | Increment via the existing mutex/atomic pattern; verified by `go test -race` |
| T-02-15 | Repudiation | inline-ignored finding can NEVER be surfaced by --show-suppressed (D-12 audit hole) | mitigate | The scanner KEEPS+annotates inline-ignored findings when ShowSuppressed is true so they reach the post-g.Wait() renderer; TestShowSuppressedInline asserts the JSON suppressed/reason fields are present (D-12) |
</threat_model>
